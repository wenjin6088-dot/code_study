## 작업 요약
`backend/src/api/auth.py`에 로그아웃 엔드포인트(`POST /api/v1/auth/logout`)를 구현했습니다. 요청에서 `refresh_token` 쿠키를 읽어서, 있으면 T025의 `UserService.logout()`에 넘겨 해당 리프레시 토큰을 DB에서 "폐기됨(revoked)" 상태로 표시합니다. 성공 시 본문 없이 204(No Content)를 돌려줍니다.

가장 중요하게 신경 쓴 부분은 "멱등성(idempotent)"입니다. 로그아웃은 다음 세 가지 상황 모두에서 에러 없이 성공 처리돼야 합니다: (1) 쿠키 자체가 없는 경우, (2) 쿠키는 있지만 DB에 존재하지 않는 값(알 수 없는 토큰)인 경우, (3) 이미 이전에 로그아웃되어 폐기 처리가 끝난 토큰인 경우. 이 세 경우를 구분해서 에러를 던지지 않고, 전부 똑같이 "성공"으로 응답하도록 만들었습니다. 이렇게 한 이유는, 로그아웃은 사용자 입장에서 "내가 로그아웃하고 싶다"는 의도이고, 서버 쪽 토큰 상태가 이미 어떻든 그 의도는 항상 달성된 것으로 봐야 하기 때문입니다. 실제로 이 멱등 처리 로직 자체는 새로 작성하지 않았는데, T025의 `UserService.logout()`이 이미 "토큰을 못 찾거나 이미 폐기됐으면 그냥 조용히 리턴한다"는 방식으로 구현돼 있어서, 라우트에서는 쿠키가 있을 때만 서비스 메서드를 호출하면 끝이었습니다.

## 기술 결정
- **상태 코드 204 선택**: 테스트는 `response.status_code in (200, 204)`로 둘 다 허용하지만, 로그아웃은 돌려줄 의미 있는 데이터가 없는 동작이라 HTTP 의미상 "본문 없음"을 뜻하는 204를 선택했습니다.
- **쿠키를 삭제(delete_cookie)하지 않음**: 서버가 브라우저의 쿠키를 지우라고 응답에 명시하는 것(`delete_cookie`)도 고려했지만, 테스트 스펙에 이 요구사항이 없고 "최소 구현" 원칙에 따라 추가하지 않았습니다. 다만 실제 프론트엔드 연동 단계에서는 사용자 경험상 로그아웃 후 쿠키를 지워주는 것이 자연스러울 수 있어, 필요 시 별도 Task로 추가하는 것을 제안합니다.
- **access_token 쿠키는 건드리지 않음**: 로그아웃 테스트들은 모두 `refresh_token` 쿠키만 다루고 있어서, access_token 쪽은 범위 밖으로 두고 손대지 않았습니다.

## 비고
- 쿠키 값을 서버 쪽에서 읽을 때, 같은 이름의 쿠키가 요청 헤더에 중복으로 들어있는 특수한 상황(아래 TASK-031의 "기술 결정" 참고)에 대비해, `request.cookies`(마지막 값 우선)가 아니라 직접 헤더를 파싱해 첫 번째 값을 우선하는 헬퍼 함수(`_first_cookie_value`)를 로그아웃에도 동일하게 적용해 일관성을 유지했습니다.
