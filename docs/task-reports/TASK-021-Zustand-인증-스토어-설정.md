# TASK-021. Zustand 인증 스토어 설정

## 상태
완료

## 작업 요약
"지금 로그인한 사람이 누구인지"는 로그인 폼, 상단 네비게이션 바, 프로젝트 목록 등 화면 여러 곳에서 동시에 알아야 하는 정보입니다. 이걸 각 컴포넌트가 따로 들고 있으면 서로 안 맞는 상황이 생길 수 있어서, "모두가 함께 보는 하나의 게시판"에 적어두고 다 같이 그 게시판만 보게 하는 방식이 Zustand 같은 전역 상태 관리 도구입니다.

`frontend/src/stores/auth-store.ts`에 `useAuthStore`를 만들었습니다.

- **`user`**: 로그인한 사용자 정보(`id`, `email`, `skillLevel`). 로그인 전에는 `null`.
- **`isAuthenticated`**: 로그인 여부를 빠르게 확인할 수 있는 플래그.
- **`setUser(user)`**: 로그인 성공 시 호출해 사용자 정보를 채우고 `isAuthenticated`를 `true`로 바꿉니다.
- **`clearAuth()`**: 로그아웃 시 호출해 전부 초기 상태로 되돌립니다.

  - `npm run build`(타입체크 + 프로덕션 빌드) 성공 — 아직 이 스토어를 쓰는 컴포넌트가 없어 실제 번들에는 포함되지 않지만, 타입 검사는 전체 소스 기준으로 통과함을 확인

    - 초기 상태 → `{user: null, isAuthenticated: false}` 정확히 확인

## 기술 결정
- **JWT 토큰 원본은 스토어에 저장하지 않음**: research.md의 인증 설계(HTTPOnly 쿠키에 JWT 저장)에 따르면, 토큰 자체는 JavaScript가 애초에 읽을 수 없습니다(HTTPOnly의 목적이 바로 XSS로부터 토큰을 보호하는 것). 그래서 이 스토어는 "토큰"이 아니라 토큰 검증 결과로 얻은 **사용자 정보와 로그인 여부**만 담습니다. Task 제목의 "JWT state"는 "JWT 인증으로 결정되는 클라이언트 측 인증 상태"로 해석했습니다.
- **`persist` 미들웨어 미사용**: Zustand는 `localStorage`에 상태를 자동 저장하는 `persist` 미들웨어를 제공하지만, 인증 상태는 쿠키(서버가 관리) 기준으로 판단해야 하므로 브라우저 저장소에 따로 사용자 정보를 캐싱하면 쿠키와 상태가 어긋날 위험이 있습니다. 새로고침 시 인증 상태를 복원하는 방법은 T038(자동 토큰 갱신)이나 앱 초기 로딩 시 `GET /auth/me`를 호출해 서버에서 다시 받아오는 방식이 더 안전하다고 판단했습니다.
- **별도 `login`/`logout` async 액션을 만들지 않음**: 실제 로그인/로그아웃 API 호출(`POST /auth/login` 등)은 T034(인증 서비스)의 책임이라고 판단해, 이 스토어는 "상태를 설정/초기화하는 순수한 상태 저장소" 역할만 하도록 최소화했습니다(YAGNI). T034에서 API 호출이 성공하면 이 스토어의 `setUser`/`clearAuth`를 호출하는 식으로 연결될 것입니다.
