# TASK-019. TanStack Query 클라이언트 설정

## 상태
완료

## 날짜
2026-11-03

## 작업 요약
프론트엔드가 백엔드 API를 호출할 때마다 매번 새로 요청하고, 로딩 상태와 에러 처리를 일일이 손으로 짜면 코드가 금방 복잡해집니다. TanStack Query(React Query)는 "서버에서 가져온 데이터를 캐시해두고, 로딩/에러/재시도를 자동으로 관리해주는" 도구입니다. 비유하자면, 매번 도서관에 가서 책을 빌리는(API 호출) 대신, 자주 보는 책은 책상 위에 꺼내두고(캐시) 필요할 때만 다시 도서관에 가는 것과 비슷합니다.

1. **`frontend/src/lib/queryClient.ts`**: `QueryClient` 인스턴스를 하나 만들고, 기본 동작 방식을 정했습니다.
   - `staleTime: 60 * 1000`(1분): 데이터를 가져온 지 1분 이내면 "아직 신선하다"고 보고, 같은 화면을 다시 봐도 서버에 재요청하지 않습니다.
   - `retry: 1`: 요청이 실패하면 1번만 재시도합니다 (기본값은 3번인데, T016에서 에러를 명확한 형식으로 응답하도록 만들어뒀으니 과도한 재시도보다는 빠르게 에러 상태를 보여주는 쪽을 선택했습니다).
2. **`frontend/src/main.tsx` (수정)**: 앱 전체를 `<QueryClientProvider client={queryClient}>`로 감싸서, 모든 하위 컴포넌트가 TanStack Query의 캐시/상태 관리 기능을 쓸 수 있게 연결했습니다.

## 기술 결정
- **`staleTime: 60초`**: research.md의 "React Query with stale-while-revalidate" 방침과 "UI 인터랙션 < 200ms" 성능 목표를 고려해, 너무 자주 재요청하지 않으면서도 1분 정도면 데이터가 크게 바뀌지 않을 것이라는 합리적인 기본값을 선택했습니다. 문서 생성 상태처럼 자주 바뀌는 데이터는 개별 쿼리에서 `refetchInterval`로 따로 오버라이드하면 됩니다(T106 등 실제 사용 시점에 결정).
- **`retry: 1`**: 기본값(3회 재시도)보다 줄인 이유는, T016에서 에러 응답 형식을 이미 통일해뒀기 때문에 실패를 빠르게 사용자에게 보여주고 다음 행동(재시도 버튼 등)을 UI가 판단하게 하는 것이 낫다고 판단했습니다. 완전히 끄지(0) 않은 이유는 일시적인 네트워크 끊김 같은 경우는 한 번의 재시도로 복구될 수 있어서입니다.
- **`refetchOnWindowFocus`는 기본값(켜짐) 유지**: 명시적으로 끄지 않았습니다. 문서 생성처럼 "다른 탭에 갔다가 돌아왔을 때 최신 상태를 보고 싶은" 시나리오가 있어서, 기본 동작(탭에 다시 포커스하면 자동 재검증)을 그대로 두는 것이 이 프로젝트의 사용 패턴에 더 맞다고 판단했습니다.
- **`QueryClientProvider`를 `React.StrictMode` 안쪽, `App` 바깥쪽에 배치**: 전체 앱(라우팅 포함)이 쿼리 캐시에 접근할 수 있어야 하므로 가장 바깥쪽에 가깝게 배치했습니다.
