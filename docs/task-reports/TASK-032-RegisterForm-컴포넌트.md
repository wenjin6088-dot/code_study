## 작업 요약
회원가입 화면에서 쓰는 입력 폼 컴포넌트를 `frontend/src/components/auth/RegisterForm.tsx`에 만들었습니다. 이메일/비밀번호/비밀번호 확인 3개의 입력칸과 "Register" 버튼으로 구성되어 있고, 사용자가 이상한 값을 입력하면 서버에 요청을 보내기 전에 화면에서 바로 막아줍니다(이메일 형식이 아닌 경우, 비밀번호가 8자 미만인 경우, 비밀번호와 확인 값이 다른 경우). 세 조건을 모두 통과했을 때만 T034에서 만든 `authService.register(email, password)`를 호출합니다.

요청이 진행 중일 때는 버튼을 비활성화해서 중복 제출을 막고, 성공하면 `onSuccess` prop으로 등록된 사용자 정보를 넘겨줍니다(이 값을 어떻게 쓸지는 호출하는 쪽, 즉 T035 Register 페이지의 책임입니다). 실패하면 서버가 보낸 에러 메시지(예: "이미 등록된 이메일입니다")를 화면에 그대로 보여주고 버튼을 다시 눌러볼 수 있게 풀어줍니다.

## 기술 결정
- **입력칸을 직접 `<input>` + `<label htmlFor>`로 작성**: 테스트가 `getByLabelText`로 요소를 찾기 때문에 label과 input의 연결만 정확하면 되고, 별도의 UI 프리미티브(예: shadcn Input)가 없어도 테스트를 통과하는 데 문제가 없어 추가 추상화를 만들지 않았습니다. 버튼만 기존 `frontend/src/components/ui/button.tsx`의 `Button`을 재사용했습니다.
- **이메일 정규식은 `/^[^\s@]+@[^\s@]+\.[^\s@]+$/`로 단순하게**: 테스트가 요구하는 것은 "`not-an-email` 같은 값을 걸러내는 것"뿐이라, RFC를 완벽히 따르는 복잡한 정규식 대신 가장 흔한 형태만 검증하도록 최소화했습니다.
- **에러 상태 하나로 모든 실패를 표현**: 클라이언트 유효성 검사 실패와 서버 에러를 같은 `error` state/문구 영역에 표시합니다. 폼이 단순해서 필드별 에러를 따로 관리할 필요가 없다고 판단했습니다.

## 비고
- `onSuccess`는 optional prop이라 RegisterForm 자체는 라우팅이나 전역 상태(zustand 등)를 전혀 모릅니다. "회원가입은 로그인이 되는 게 아니다"라는 백엔드 계약(별도 쿠키가 설정되지 않음)에 따라, 가입 후 어디로 이동할지는 T035 Register 페이지에서 결정합니다.
- 테스트 파일 전체를 실행했을 때 같은 파일 안에서 여러 번 `render()`를 호출하는데, 프로젝트의 `frontend/tests/setup.ts`에 테스트 종료 후 DOM을 정리하는 `cleanup()` 호출이 없어서 "버튼이 여러 개 발견됨" 오류가 났습니다. 이는 RegisterForm 코드 자체의 문제가 아니라 테스트 환경 설정의 공백이라 판단해, 테스트 파일은 건드리지 않고 `tests/setup.ts`에 `afterEach(() => cleanup())`를 추가해 해결했습니다(T033~T038의 다른 컴포넌트 테스트도 동일하게 영향을 받던 문제였습니다).
