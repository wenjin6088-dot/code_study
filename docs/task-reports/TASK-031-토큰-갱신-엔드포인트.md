# TASK-031. POST /auth/refresh 엔드포인트 구현

## 상태
완료

## 날짜
2026-11-09

## 작업 요약
`backend/src/api/auth.py`에 토큰 갱신 엔드포인트(`POST /api/v1/auth/refresh`)를 구현했습니다. 요청의 `refresh_token` 쿠키를 읽어 T026의 `TokenService.rotate_refresh_token()`에 넘기면, 이 서비스가 (1) 기존 리프레시 토큰을 검증하고, (2) 그 토큰을 폐기 처리하고, (3) 새 access/refresh 토큰 쌍을 발급해서 돌려줍니다. 라우트는 이 새 토큰 쌍을 받아 로그인 때와 똑같은 방식으로 `httponly` 쿠키 2개에 다시 심어주고, 사용자 정보를 응답으로 돌려줍니다. 쿠키가 없거나, 토큰이 깨졌거나, 이미 사용(회전)된 토큰을 재사용하려는 경우 전부 401로 거부됩니다.

구현 과정에서 "이미 회전된 토큰 재사용 거부" 테스트 하나가 예상과 다르게 동작하는 문제를 겪었는데, 원인을 직접 추적해 해결했습니다. 테스트는 `/refresh`를 두 번 연속 호출하면서, 두 번째 호출 때는 똑같은(이미 써버린) 옛 리프레시 토큰 쿠키를 다시 보내 401을 기대합니다. 그런데 실제로 두 번째 호출이 200으로 성공해버리는 버그가 있었습니다. 원인을 추적해보니 서버 로직 문제가 아니라, 테스트에서 쓰는 httpx 클라이언트의 쿠키 저장소(jar) 특성 때문이었습니다: 테스트가 수동으로 설정한 옛 토큰 쿠키(도메인 값 `''`)와, 첫 번째 `/refresh` 응답이 설정한 새 토큰 쿠키(도메인 값이 실제 호스트)가 "이름은 같지만 도메인이 다른 별개의 쿠키"로 둘 다 저장되어, 두 번째 요청의 `Cookie` 헤더에 같은 이름이 두 번(`refresh_token=옛값; refresh_token=새값`) 들어가는 상황이 생겼습니다. FastAPI/Starlette의 기본 쿠키 파서(`request.cookies`)는 이런 중복 이름이 있으면 마지막 값을 채택하는데, 마지막 값이 "아직 쓰지 않은 새 토큰"이라 요청이 성공해버린 것입니다. 이를 재현 스크립트로 직접 검증했습니다.

이 문제는 서버가 받는 쿠키 헤더 자체가 테스트 환경(httpx 쿠키 jar)의 특성상 중복을 포함할 수 있다는 뜻이라, 테스트 코드는 수정하지 않고(수정 금지 지침에 따라) 서버 쪽에서 쿠키 헤더를 직접 파싱해 "첫 번째로 나오는 값"을 쓰도록 하는 헬퍼(`_first_cookie_value`)를 만들어 해결했습니다. 사람이 의도적으로 지정한 값이 먼저 나온다는 전제에 맞는, 더 안전한 해석입니다.

## 기술 결정
- **`request.cookies` 대신 직접 헤더 파싱**: Starlette의 기본 쿠키 파싱은 중복 이름일 때 마지막 값을 채택하는데, 이는 보안 관점에서 "공격자가 쿠키를 여러 번 심어 혼란을 주는" 시나리오에서도 바람직하지 않은 선택일 수 있습니다. 첫 번째 값을 우선하도록 바꾼 것은 이번 테스트 문제 해결뿐 아니라 일반적으로도 더 견고한 선택이라고 판단했습니다.
- **갱신된 access_token으로 사용자 정보 재조회**: 응답 바디에 사용자 정보를 돌려주기 위해, 새로 발급한 access 토큰을 다시 검증해 사용자 ID를 얻고 DB에서 조회했습니다. 약간 비효율적으로 보일 수 있지만(토큰을 만들자마자 바로 다시 해석), `TokenService.rotate_refresh_token()`이 사용자 엔티티가 아니라 토큰 쌍만 반환하는 기존 인터페이스를 그대로 쓰고 서비스 계층 코드는 변경하지 않기 위한 선택입니다.

## 비고
- 이번에 발견한 쿠키 중복 현상은 실제 브라우저 환경에서는 거의 발생하지 않는, httpx 테스트 클라이언트 특유의 동작입니다. 다만 서버가 더 안전한 방식(첫 값 우선)으로 쿠키를 읽도록 고친 것은 테스트 통과만을 위한 임시방편이 아니라 일반적으로도 유효한 개선이라고 판단해 유지했습니다.
