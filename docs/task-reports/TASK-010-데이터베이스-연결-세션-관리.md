## 작업 요약
지금까지는 DB에 직접 `psql` 명령으로 접속해서 테이블을 확인했습니다. 하지만 실제 FastAPI 서버는 요청이 들어올 때마다 Python 코드로 DB에 접속해야 합니다. "매번 새로 전화를 걸 필요 없이, 미리 뚫어둔 전화선(연결 풀)을 돌려쓰는" 역할을 하는 코드를 만들었습니다.

`backend/src/db/session.py`에 세 가지를 정의했습니다.

1. **`engine`**: DB로 가는 "도로"입니다. `DATABASE_URL` 환경변수(T005에서 만든 `.env.example`의 `postgresql+asyncpg://...` 값)를 읽어서, 비동기(async) 방식으로 PostgreSQL에 연결할 준비를 합니다. `pool_pre_ping=True`를 켜서, 오랫동안 안 쓰여서 끊어진 연결을 재사용하려다 에러나는 상황을 방지합니다 (연결을 실제로 쓰기 전에 살아있는지 가볍게 확인).
2. **`AsyncSessionLocal`**: "대화 창구"를 만드는 공장입니다. 호출할 때마다 새로운 DB 세션(하나의 대화)을 만들어줍니다.
3. **`get_db()`**: FastAPI가 각 API 요청마다 자동으로 호출해줄 함수입니다. 세션을 하나 열어서 API 코드에 넘겨주고, 요청이 끝나면 자동으로 세션을 정리(닫기)합니다. (`async with` 구문을 쓰기 때문에, 중간에 에러가 나도 세션이 제대로 닫힙니다.)

## 기술 결정
- **`DATABASE_URL`을 `os.environ`에서 직접 읽음**: T011("데이터베이스 설정 및 커넥션 풀링")이 아직 구현되지 않은 상태라, 공용 설정(config) 모듈에 의존하지 않고 이 파일 안에서 직접 환경변수를 읽도록 했습니다. tasks.md에 T010과 T011이 둘 다 `[P]`(병렬 가능, 서로 의존하지 않음)로 표시되어 있어, 이렇게 독립적으로 동작하게 만드는 것이 설계 의도에 맞다고 판단했습니다. T011이 구현되면, 필요에 따라 이 파일이 공용 설정 모듈을 사용하도록 리팩토링할 수 있습니다.
- **비동기(`AsyncSession`, `async_sessionmaker`) 방식 사용**: research.md와 T008/T009에서 이미 "SQLAlchemy 2.0 async + asyncpg" 방향으로 일관되게 결정되어 있어, 동기 방식 세션이 아닌 비동기 방식으로 작성했습니다.
- **`expire_on_commit=False`**: 커밋 후에도 세션에서 가져온 객체의 속성을 추가 쿼리 없이 그대로 읽을 수 있게 하기 위한 일반적인 FastAPI+SQLAlchemy 비동기 패턴입니다. API 응답을 만들 때 커밋 직후 객체 속성에 접근하는 경우가 많아서 필요합니다.
- **`pool_pre_ping=True`**: 데이터베이스가 재시작되거나 유휴 연결이 끊긴 경우에도 "연결은 있는데 죽어있는" 상태로 쿼리를 시도해 에러나는 것을 막기 위해 켰습니다. 약간의 오버헤드가 있지만, 안정성이 더 중요하다고 판단했습니다.
